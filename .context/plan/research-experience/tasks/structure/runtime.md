# STATADIC runtime and pytest structure audit

Scope: `src/python/packages/statadic/src/statadic` and its standalone `tests`, read-only survey on 2026-11-04. Paths below are relative to `src/python/packages/statadic/`. Sizes are current `wc -l` observations, used only to locate candidates; responsibilities and coupling, not line count, justify moves. Internal studies-app reorganization is intentionally excluded. This is a proposed sequence, not an instruction to change code or a claim that all paths are private.

## Design decision

Retain the architecture's **role first, family second**: e.g. `api.panel` composes workflows; `estimation.panel` fits; `operators.panel` prepares indexing; `inference.panel` interprets uncertainty. These layers should be discoverable by the same family vocabulary, but should not be assembled under a single top-level `panel` facade or forced into identical directory trees. A small `model.glm.py` or `operators.panel.py` is a legitimate implementation owner even when estimation is a package. Separate numerical algorithms in `optimize` and reusable structures in `core` from the model family using them. The existing `estimation.dyadic/{contracts,fit,solve}.py`, `estimation.gel/{fit,_dual}.py`, and `discrepancy/mmd/{scalar,matrix,weighted,contracts}.py` are useful examples: cohesive components, curated family exports and no duplicate cross-layer facade. `api.regression/{_linear,_glm}.py` is the analogous public-host/private-implementation pattern.

## Ranked runtime candidates

1. **Panel: create a coherent estimator family; separate workflow preparation.** `src/statadic/estimation/panel.py` (705 lines) mixes two fit carriers (`PanelFit`, `FamaMacBethFit`, lines 64, 113), shared problem/assembly, five panel estimators and the periodwise Fama–MacBeth path (229–571, 574–705). Proposed `estimation/panel/__init__.py` (curated existing exports), `contracts.py` (fits/problem), `_common.py` (array preparation and assembly), `static.py` (pooled, within, between, first differences and random effects), `fama_macbeth.py` (fit and estimator). Split `static.py` further only if ownership remains clear after extraction. `src/statadic/api/panel.py` (584 lines) separately owns static result/model orchestration (130–403) and host spatial-panel alignment/effect design (405–584); a companion `api/panel/{__init__,_regression,_spatial_data}.py` is a reasonable second step, retaining imports for `PanelRegression`, `PanelOLS`, `SpatialPanelData`, `prepare_spatial_panel_data` and `prepare_panel_effect_design`. The latter is consumed across spatial workflows, not a second panel estimator. `operators/panel.py` (376 lines) already owns index and transformations and need not move just to mirror the estimator package. `inference/panel_covariance.py` (312 lines) has both conventional panel and Fama–MacBeth covariance (215, 283): candidate `inference/panel/covariance.py`, with `inference/panel/__init__.py` curated exports; document the intentional old-to-new import break.

2. **GMM estimation: separate solve/iteration mechanics from retained fit and public estimators.** `estimation/gmm.py` (632 lines) contains `AffineGMMFit` (101), array preparation and weighted solve (160–243), iteration (244–318), fit assembly and diagnostics (319–583), and public `IteratedGMM`/`FixedWeightGMM` (584–632). Proposed `estimation/gmm/{__init__,contracts,_solve,_fit,estimators}.py`; keep `_solve` and `_fit` private, avoid cycles between fit carrier and numerical assembly. `estimation/moments.py` supplies both fixed and affine problem types for GEL as well as GMM: keep it shared instead of hiding it under GMM. `inference/gmm/{covariance,hypothesis}.py` is already a meaningful package; `hypothesis.py` (545 lines) hosts Wald, generic moment Hansen J and fitted-model Hansen J, so optional later split `hypothesis.py` into `wald.py` and `hansen.py`, updating the established public-submodule imports as an intentional clean break. `api/moments.py` (331 lines) deliberately composes GMM and GEL, and should not be blindly mirrored into `api/gmm`.

3. **Spatial-panel internal names encode subfamilies but are already discoverable; choose a targeted split only if a separate change needs it.** `estimation/spatial/panel.py` (801 lines) combines `SpatialPanelProblem`/`PanelML`/fit, profiles, three information routes and a search/final fitting pipeline (lines 57–128, 242–454, 455–801). `observed_panel.py` (503) separately owns observed-subvector contracts, likelihood, search, joint information and fit (28–354). Proposed internal paths `estimation/spatial/panel/{__init__,contracts,profile,_information,_search,fit}.py` for the complete-panel lane, and keep observed-panel distinct or place it in `estimation/spatial/observed_panel/` only when it too benefits from independent internal components. Preserve `estimation.spatial.panel.spatial_panel_profile` and root `estimation.spatial` exports, because tests import both. `api/spatial/_panel.py`, `_observed.py`, `_cross_section.py` are already a useful private family partition. `operators/spatial/{weights,moments}.py` and `inference/spatial/{covariance,diagnostics}.py` own distinct layers, not duplicates. A migration must avoid implying that observed-subvector and balanced-panel likelihoods share missing-data semantics.

4. **GLM estimation: modest, not taxonomy-driven, separation.** `estimation/glm.py` (610 lines) combines `GLMFit`, host/array validation, common solve/assembly, binomial/Poisson adapters, problem/estimator classes and prediction (lines 79, 142–426, 427–561, 562 onward). Proposed `estimation/glm/{__init__,contracts,_fit,estimators,prediction}.py`; make family-specific kernels private alongside the fit implementation unless there is a real independent reuse. `model/glm.py` (91) is already a cohesive shared equation and family likelihood owner; `optimize/glm.py` owns solver and existence certificate; `api/regression/_glm.py` owns host lifecycle—do not collapse them. `inference/glm_covariance.py` (139) could become `inference/glm/covariance.py` alongside its curated initializer only if the suffix normalization below is adopted; a one-file package alone provides limited value.

5. **Inference family suffixes: normalize at real family boundaries, selectively.** `inference/linear_covariance.py` (305 lines) owns classical, HC, HAC and cluster parameter uncertainty (159–305); `inference/panel_covariance.py` (312) handles panel/cluster/Fama–MacBeth; `inference/glm_covariance.py` (139) handles model/HC GLM. They encode `family.operation` in one filename while `inference/gmm/covariance.py`, `inference/spatial/covariance.py`, `inference/survival/information.py` already use directories. Proposed eventual canonical imports `inference.linear.covariance`, `inference.panel.covariance`, `inference.glm.covariance`; document the clean import break and update consumers together. Keep `inference/parameters.py` (449) shared; its reference laws, generic interval/restriction tests and covariance capabilities serve many families. Avoid creating `inference/linear/parameters.py` or duplicate implementations. For GLM, defer the package if no second module materializes and import migration cost outweighs consistency.

6. **Ground geometry: split implementation by actual conceptual boundaries, not one file per metric.** `geometry/ground/metrics.py` (910 lines) contains law descriptors (147–250), pointwise Euclidean/angular/cosine variants (251–454), branded strategies, and checked/cloud pairwise dispatch (745–910). Consider `geometry/ground/metrics/{__init__,laws,_pointwise,strategies,pairwise}.py`; `similarities.py` (499 lines) bundles Gram producers, distance-induced construction, RBF strategy and dispatch (126–456), candidate `similarities/{__init__,gram,rbf,_dispatch}.py` only if import and type dependencies remain acyclic. Preserve `geometry.ground.metrics` and `.similarities` imports and public strategy identities, including direct module consumers. Existing `_strategy.py` and `_similarity_strategy.py` encode private strategy boundaries and may remain where they are. Do not split each small distance into its own module.

7. **Core contract modules: defer deep subdivision until dependency graph is mapped.** `core/domains.py` (860) couples space descriptors, object-domain types, construction origins, law/evidence carriers and transformations (176–480, 553–833); `core/equations.py` (852) couples descriptor types/carriers and sandwich/parameter covariance composition (118–379, 417–852); `core/matrices.py` (793) couples descriptors, carriers, checking and constructors (162–490, 517–734); `core/statistics.py` (721) couples semantic descriptors and realized carriers (150–401, 470–686). A potential `core/equations/{__init__,descriptors,carriers,_composition}.py` extraction is the clearest first experiment; keep shared descriptor identities singular and prevent lower-level contracts from importing estimation or inference. Similar future `core/matrices/{contracts,checking,construction}.py` is plausible, but matrix/domain/statistics type parameters and forward references are tightly coupled; do not perform a mechanical universal split. These are public qualified type paths and potential pickle identities; any move needs compatibility and typing review.

8. **Initializer work: distinguish a large public surface from a monolith containing implementation.** `core/__init__.py` (175) has an extensive eager compatibility surface and even `LegacyDMat` (line 142), despite architecture preferring navigation-only root/compound initializers. `geometry/ground/__init__.py` (144) eagerly exports config, distance and similarity objects. `discrepancy/transport/__init__.py` (120) and `discrepancy/mmd/energy/__init__.py` (118) also deserve an import-time/export inventory. These are lists/reexports, not algorithm monoliths: moving them merely to reduce LOC is not useful. Audit real imports, `__all__`, circularity and import cost; direct users toward owner modules and document any intentional removal as a clean import break. `core.LegacyDMat` is an explicit alias: deleting it as redundant changes API. `estimation.gel` and `estimation.dyadic` initializers (4 and 20 lines) are good examples of selective family curation, not proof that every family must have equally short exports.

9. **Survival is already grouped; preserve model distinctions.** `model/survival/{aft,spatial}.py`, `estimation/survival/{fit,spatial,refinement}.py`, `inference/survival/information.py` and `api/survival/{_model,_spatial,inference}.py` follow role/family ownership. `estimation/survival/spatial.py` (529) includes period preparation (53–144), problem/fit, joint likelihood, and `SpatialSurvivalML` (378 onward); if new work demands a split, move the period/problem/fit carrier and preparation to `estimation/survival/spatial/{contracts,prepare}.py`, joint likelihood to `_likelihood.py` and estimator to `fit.py`, retaining `estimation.survival.spatial` and family exports. Keep adaptive `refinement.py` separate and don't model joint spatial likelihood as iid rowwise scores. Otherwise the current layout is preferable to more empty layers.

## Migration and verification implications

Changing a `.py` module to a same-named package can keep common imports (`from statadic.estimation.panel import Within`) if `__init__.py` reexports the exact same objects. It does **not** automatically preserve direct imports from old private helpers, class `__module__` qualified names, serialization/pickle references, introspection, API/autodoc anchors, `__all__`, import cycles or public inventory records. A compatibility reexport preserves object identity within one process but may change its qualified-name metadata. Follow the documented clean-import-break policy: update imports and the migration guide together without compatibility facade trees; disclose affected serialized class identities. A proposed future move still requires user authorization. Never use `sys.modules` mutation or magic lazy imports to conceal moves.

Before each approved batch: inventory real imports across runtime, tests, notebooks, docs, apps and Lean public API/correspondence registries; classify public/private and persisted names. Preserve semantically meaningful behavior, dtype and JAX tracing, component contracts, source correspondence pins and algorithm identity. Move associated tests with imports, preserve `pytest --import-mode=importlib`, check conftest scope and relative imports (`tests/inference/test_permutation.py` imports `.conftest`; several tests import `.._typing`, `.._validation`, `inference._moments`). Check duplicate pytest basenames and collection IDs, explicit path selections in scripts, CI, docs/release JUnit and coverage config. Run targeted family and cross-layer tests first, both precision modes where required, package type/import/API/standalone-wheel and sdist checks, followed by `just check`. Preserve external-reference and qualification markers and compare collection counts before/after. Public inventory and formal source pins require explicit review/synchronization; tests must never silently repin them. Run full scientific qualification separately only when its acceptance scope requires it; a structural refactor cannot inherit proof or qualification merely from passing imports.

## Supplement: optimization, sample evidence and reporting

The previous compatibility wording is superseded by the package's actual `docs/module-organization.md`: prior moves are intentional clean import breaks, without compatibility facade trees or `sys.modules` mutation, and external pickles may need migration. The proposals below follow that policy; retaining an unchanged *family* import through its new canonical `__init__` is ordinary family curation, not a promise to preserve every old qualified name. Update docs, registries and consumers in the same authorized change and call out any public-path break.

### Simplex and nonnegative QP — high-value separation, with distinct domains

`src/statadic/optimize/simplex.py` is 1,087 lines and supplies three genuinely distinct numerical contracts: batched nonnegative-cone quadratic programming (`NonnegativeQPSolution` line 141, sanitization/coordinate solver 185–548, public entry 461); projected-gradient simplex operations, including affine stopped iterations and `SimplexSolution` (549–808; carrier line 79); and capped-simplex QPAX solve plus tangent convexity/KKT evidence (`SimplexQPSolution` line 105, code 809–1087). The nonnegative solver has no sum-to-one constraint; presenting it as a simplex algorithm is a semantic discovery problem as well as a long-file problem. Proposed canonical destinations:

- `optimize/simplex.py` projected-gradient and simplex-QP operations -> `optimize/simplex/{__init__,projected_gradient,qp}.py`, with result carriers either beside their corresponding solvers or in a small `contracts.py` if there is actual shared use.
- `optimize/simplex.py::batched_nonnegative_quadratic_program` and `NonnegativeQPSolution` -> `optimize/nonnegative_qp.py` (or `optimize/quadratic/nonnegative.py` only if another nonnegative quadratic owner develops); the latter is a clean public import change, not a simplex-constrained method. Make any actually shared low-level tolerance/sanitization helper private and avoid inventing an umbrella facade.
- `tests/optimize/test_simplex.py` (469 lines) spans nonnegative tests at 35–243 and 342–393, and simplex projected-gradient tests at 258–307 and 394–469. Split by tested method into `tests/optimize/test_nonnegative_qp.py` and `tests/optimize/simplex/test_projected_gradient.py`. Move `test_simplex_diagnostics.py` (152; affine convergence/precision/JIT/vmap) -> `tests/optimize/simplex/test_diagnostics.py`; `test_simplex_qp.py` (402; capped QP, independent SciPy and tangent convexity) -> `tests/optimize/simplex/test_qp.py`. `tests/migration/test_t56_4_inequality_solvers.py` and `tests/migration/test_kernels_migration.py` are independent migration evidence: update imports but retain category. `inference/gms.py`, `inference/wolak.py`, `inference/_projection.py` call the nonnegative solver; balancing and barycentre consumers use simplex PGD. Preserve key schedules, result/status metadata, gradients/JIT behavior and dtype; tests must not infer that nonnegative cone and probability simplex constraints are interchangeable.

### PSD repair — nearest-correlation algorithm versus repair alternatives

`src/statadic/optimize/psd.py` is 947 lines. The Qi–Sun dual Newton path (PSD projection, Loewner Jacobian, conjugate gradient, line search, `NearestCorrelationResult`, `nearest_correlation` and covariance wrapper; 288–724) has a cohesive convergence/error contract distinct from baseline ridge, eigendecomposition clipping and diagonal shrinkage (725–867), and comparative `RepairDiagnostics` (868–947). Proposed `optimize/psd/{__init__,nearest,spectral,diagnostics}.py`: place the nearest solver's numerical helpers privately with `nearest.py`, keep `ridge_psd`/`eig_clip`/`gerber_shrink_psd` in `spectral.py` only where their actual calculations and imports make that grouping coherent, and return existing public names at the curated `statadic.optimize.psd` family boundary. Move the lengthy solver-history prose to a linked design or evidence record after verifying claims and paths; preserve precision/convergence warnings and references in the owner documentation. No new mathematical algorithm or broader proof claim follows from the split.

`tests/optimize/test_psd.py` (863 lines) has separable nearest/oracle/covariance-preserving tests (254–333, 387–678), spectral baseline and derivatives (169–253, 334–386, 716–794), and common diagnostics and JAX transforms (679–715, 795–862). Split into `tests/optimize/psd/test_nearest.py`, `test_spectral.py`, `test_diagnostics.py` only after extracting the shared independent Dykstra oracle and fixtures once within that test family. Cross-repair tests (e.g. nearest versus clipping and `test_every_repair_transforms_with_a_static_result_structure`) remain explicit integration tests, e.g. `test_comparison.py`; do not duplicate oracle logic. `tests/operators/test_covariance.py` exercises use of ridge and remains operator-owned. Tests must preserve cases around stalled convergence, float32 overclaim protection, exact variances, near-switch derivatives, and reference tolerances.

### Sample evidence — split doors from transformations without crossing population authority

`src/statadic/sample/evidence.py` is 952 lines, but its central design is coherent: `CheckedClouds`, sealed minting and separate support/pooled metadata (169–257); `PopulationHypotheses` and explicit declaration (258–280, 915–952); eager active-row checking and safe normalization (281–673); preserving selection/permutation/concatenation (674–792); and evidence-forgetting value-changing operations (793–914). A justified package is `sample/evidence/{__init__,contracts,_checking,checks,transforms,population}.py`: `_checking.py` owns masked host validation, `checks.py` owns explicit evidence doors, `transforms.py` owns operations with clear preservation/erasure guarantees, and `population.py` owns declarations only. Ensure the single mint capability stays private to the authorized producer modules, marker metadata remain static pytree metadata, and padded NaN/zero rows are excluded rather than reinterpreted. No observed finite sample may mint `PopulationHypotheses`. `statadic.sample.evidence` stays the curated owner, not a second facade under `core.domains`: core owns the reusable semantic evidence types, sample owns the empirical checked carrier and actual doors, and `sample.packed` owns raw representation.

`tests/sample/test_evidence.py` (640) already witnesses antipodal versus pooled distinctions (294–324), invalid values/active padding and counts (325–400, 476–521), preservation versus erasure and private minting (401–475), pytree/JIT/vmap (522–589), and declared population versus sample evidence including static typing checks (590–640). If maintaining it becomes difficult, split `tests/sample/evidence/{test_checks,test_transforms,test_pytree,test_population}.py`, keeping shared fixture/support once and static-type tests on their own marked lane; retain `tests/geometry/ground/test_ground.py` and `tests/testing/test_testing.py` as cross-layer integrations. Coordinate with the separate population/sample audit before proposing or carrying out that split; evidence visibility is a trust boundary, not merely a filesystem detail.

### Reporting — snapshot model, plot semantics and renderers

`src/statadic/api/reporting.py` is 613 lines and contains recursive immutable metadata conversion (36–69), report row/metric carriers and validation (92–198), `ReferenceLine` and `PlotSpec` with Matplotlib export (200–342), PGFPlots formatting (343–408), and `Report` with text, HTML and LaTeX renderers (409–613). A reasonable optional extraction is `api/reporting/{__init__,metadata,models,plot,render}.py`, with `Report`, `ParameterRow`, `Metric`/`finite_metric`, `PlotSpec`, `ReferenceLine`, and `render_pgfplots` exported through the curated family namespace. Avoid circular imports by keeping pure formatting helpers independent of carriers or by placing renderer functions below model contracts with thin carrier methods that delegate. Matplotlib remains optional and imported only when plotting is requested; renderer extraction must not force its import at `import statadic.api.reporting`. These reports preserve unavailable inference, unrounded values, finite validation, escaped labels and metadata; they must not recalculate statistical quantities.

`tests/api/test_reporting.py` (199) already covers immutable metadata, nonfinite/unavailable values, escaping, plot-coordinate agreement and interval semantics. Keep it intact initially because it covers a single public report contract; if renderer-specific growth warrants splitting, place under `tests/api/reporting/{test_models,test_renderers,test_plot}.py` while keeping a shared end-to-end rendering test. `tests/api/test_artifacts.py`, `test_workflows.py`, `test_base_lifecycle.py` and many actual host workflows consume these report types: these are integration consumers, not misplaced reporting unit tests. Preserve text/HTML/LaTeX output, plot semantics, optional dependency behavior, reporting metadata and any persisted serialization format across the refactor.
