## Findings and disposition

1. **Package build consistency: addressed for ordinary persistent changes.** The installed preparation originally snapshotted lock/project/catalogue metadata but built STATADIC, evidence and studies wheels sequentially without checking package source changes during those builds. This could retain mutually inconsistent wheels while individual wheel verification passed. Current `src/python/apps/studies/src/statadic_studies/installation.py::_build_inputs` recursively fingerprints all three package trees, excluding build/cache output, before wheel builds; `prepare` recomputes the inventory after builds and aborts if additions, deletions or content changes persist. The retained preparation manifest records the input fingerprint map. `tests/test_installation.py::test_prepare_builds_offline_hash_locked_noneditable_closure` now includes a nested source mutation during a mocked build and requires failure before the completion manifest. The installer agent reported seven focused tests passed; I inspected the implementation and regression but did not independently rerun them. Two snapshots are not an atomic build snapshot: a transient source mutation reverted between scans is not detected. If a future guarantee requires protection against that class, build from a retained immutable source tree or otherwise bind each wheel to an immutable input.

2. **Third-party dependency bytes on resume: assurance wording corrected; limitation remains.** Initial third-party requirements install uses the locked requirements with `--require-hashes`, and each of the three retained workspace wheels is checked against its noneditable installed payload. `_probe` subsequently compares installed third-party distribution versions and import origins; it does not verify every third-party installed source or binary against its wheel on resume. `src/python/apps/studies/README.md` and the preparation payload now explicitly state that later same-version third-party payload changes are not detected. That resolves the overclaim by narrowing assurance, not by adding third-party payload attestation. The hash-checked initial install, workspace-wheel byte checks, frozen source capsules and version checks remain useful within their stated boundaries.

No additional high-confidence P1/P2 scientific or assurance defect was established during the sampled review. This is not a blanket correctness certification.

## Release gate and installed scope

The current scientific release gate checks complete catalogue/source-review state, retained evaluation profile and trial/draw budgets, installed-wheel identity, CPU float64 scope and current runner/source/dependency-version identities. It rejects source-only and smoke evidence for qualification. These checks are compatible with preserving adverse results, but cannot create primary-source correspondence or scientific validity from a completed run. Installed preparation retains three noneditable wheels, lock/metadata and reference snapshots; the current README correctly limits third-party mutation assurance as described above.
