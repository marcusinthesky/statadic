● Exemplary docs in the PyData ecosystem

  Project: scikit-learn
  What it does especially well: Often cited as the gold standard. The User Guide

    covers the concepts and math. The API reference is generated from numpydoc
    docstrings. The example gallery is built with sphinx-gallery and runs in CI.

    Every API page links back to its User Guide section and to the examples that

    use it, so you can always move between the three. It also has an excellent
    Glossary that pins down terms like "estimator" and random_state, and a
    "choosing the right estimator" flowchart.

    docstring standard that most of the ecosystem uses.

  Project: pandas

  Project: Matplotlib

  Project: Hypothesis
  What it does especially well: A clean, recent restructure into tutorial,

  Outside Python, two references are worth studying for statistical software:
  - Stata's PDF manuals. Every command entry follows the same layout: Syntax,
    Description, Options, Remarks and examples, Stored results, Methods and
    formulas, References. For statistical reference docs this is hard to beat.
  - R package vignettes, such as those for fixest and lme4. Each is a long-form
    narrative tied to one package.

  Frameworks people recommend

  1. Diátaxis (Daniele Procida), the dominant one

  Docs serve four distinct reader needs, laid out on two axes:

  ┌─────────┬─────────────────────────────────┬─────────────────────────────┐
  │         │   Studying (acquiring skill)    │  Working (applying skill)   │
  ├─────────┼─────────────────────────────────┼─────────────────────────────┤
  │ Doing   │ Tutorials: learning-oriented    │ How-to guides:              │
  │         │                                 │ goal-oriented               │
  ├─────────┼─────────────────────────────────┼─────────────────────────────┤
  │ Knowing │ Explanation:                    │ Reference:                  │
  │         │ understanding-oriented          │ information-oriented        │
  └─────────┴─────────────────────────────────┴─────────────────────────────┘

  The main point is don't mix the types. A tutorial that stops to explain theory
  loses the beginner. A reference page that teaches becomes hard to scan. Most
  bad docs are one long page trying to be all four.

  - Tutorials: the reader is guaranteed to succeed. Make it concrete, offer no
    choices, keep explanation to a minimum, and show real output. You are
    responsible for the learner getting through it.
  - How-tos: titled by goal ("How to fit clustered standard errors"). Assume the
    reader is competent and skip the preamble.
  - Reference: plain, complete and consistent. Its structure mirrors the code.
    It describes rather than instructs.
  - Explanation: the why. This covers design decisions, trade-offs, theory and
    alternatives (your ARCHITECTURE.md is already this).

  2. Minimalism (John Carroll, The Nurnberg Funnel)

  This came before Diátaxis and underlies it. Let users start real tasks
  immediately, cut any text that doesn't support action, and support recognizing
  and recovering from errors. In practice that means showing what wrong output
  looks like and documenting the common exceptions.

  3. "Every Page is Page One" (Mark Baker)

  Most readers arrive from search, so each page has to stand on its own. State
  the context up front, link to prerequisites rather than assuming the reader
  followed a path, and keep the scope to one topic.

  4. Learner-centered design (Greg Wilson, Teaching Tech Together; Software
  Carpentry)

  - Write for named personas: novice, competent practitioner, expert. Each needs
    a different kind of doc.
  - Respect cognitive load: introduce one new concept per step.
  - Novices lack a mental model, while experts need the details. A concept map
    or a "core concepts" page bridges the two.

  5. Docs-as-code and executable docs

  Docs that aren't tested drift out of date. The common practice:
  - Doctests run inside the Examples section of every docstring.
  - Executed galleries and notebooks in CI, using sphinx-gallery, myst-nb or
    mkdocs-jupyter.
  - Link checking and prose linting, for example Vale with the Google or
    Microsoft style guides.

  6. The numpydoc docstring contract

  The sections are Parameters, Returns, Raises, See Also, Notes (math and
  algorithm), References (citations) and Examples (runnable). See Also and
  Examples are what connect reference pages to each other and to the rest of the
  docs.

  Patterns worth copying, especially for a statistics library

  1. A "getting started" page with a fast time to first success: install, then
     one meaningful result in under five minutes, then a "where to go next" map.
  2. Two-way links between narrative docs and the API, as scikit-learn does.
     Each reference entry links to the guide and examples that use it, and each
     guide links to the API.
  3. Rigorous statistical reference. For each estimator, give the model
     definition, assumptions, the estimator and variance formulas, defaults, how
     missing values and edge cases are handled, the numerical method,
     citations, and stored or returned attributes.
  4. Equivalence with other software. State something like "This matches Stata
     reg y x, vce(cluster g) / R fixest::feols", ideally backed by tests that
     check against reference outputs. Statistical users trust results that have
     been checked against a known implementation.
  5. Migration pages ("coming from Stata / R / statsmodels") that map idioms
     side by side.
  6. A glossary, so terms like "weight", "cluster" and "fixed effect" each have
     one meaning across the whole site.
  7. Changelog, deprecation policy and versioned docs, so readers know which
     version a page describes.

  Further reading

  - https://diataxis.fr. Short, and worth reading in full.
  - NumPy NEP 44, a real-world case study of applying Diátaxis.
  - Jacob Kaplan-Moss, "Writing Great Documentation" (2009), the essay series
    behind Django's well-regarded docs.
  - Docs for Developers (Bhatti et al.) and Docs Like Code (Anne Gentle).
  - The Good Docs Project, which has templates for each page type.
  - The Scientific Python Development Guide's documentation section.

     │ Philosophy                                                              │
     │                                                                         │
     │ 1. Diátaxis, one type per page. Every page declares type: in            │
     │    frontmatter: tutorial, how-to, reference, explanation, landing,      │
     │    evidence or blog. A Schematter schema for that type fixes its        │
     │    sections, their order and their token limits.                        │
     │ 2. The site is for users. Contributor, release and process material     │
     │    lives in repo Markdown: CONTRIBUTING.md, the package                 │
     │    ARCHITECTURE.md, apps/*/README.md and infra/release/README.md.       │
     │    Change history lives in CHANGELOG.md.                                │
     │ 3. Every fact has one home.                                             │
     │    - Assumptions, limits and evidence for a method appear once, in that │
     │      method's reference page under ## Assumptions and limits and ##     │
     │      Evidence.                                                          │
     │    - Tutorials and how-tos link there once instead of repeating         │
     │      caveats.                                                           │
     │    - Concepts explain once, and other pages link to them.               │
     │ 4. Runnable code comes from executed notebooks. Tutorials and how-tos   │
     │    are marimo notebooks, executed at build time. Reference snippets are │
     │    short and are tested (see Phase 5).                                  │
     │ 5. The author's voice is the standard, and it is quantified and checked │
     │    (next section).                                                      │
     │                                                                         │
     │ Style guide (src/python/apps/docs/STYLE.md, linked from CONTRIBUTING)   │
     │                                                                         │
     │ Hard rules. These are gated by scripts/check_prose.py on every page and │
     │ on notebook prose.                                                      │
     │ - No semicolons in prose; write two sentences instead.                  │
     │ - No sentence longer than 40 words.                                     │
     │ - No internal vocabulary on user pages:                                 │
     │   - Ticket and paper IDs: \bt\d+(\.\d+)*\b, Paper \d, W\d+, T\d+.       │
     │   - Process words: qualification, qualified, campaign, witness, lane,   │
     │     ledger, disposition, registration, retained (as an adjective),      │
     │     brick, door, waist, slice, delivery, publication hold.              │
     │   - Changelog words: former, no longer, has been removed, now + verb.   │
     │   - evidence pages get a narrower allow-list, for example provenance.   │
     │ - No more than one negation sentence ("does not / is not / neither / no │
     │   …") per paragraph outside ## Assumptions and limits.                  │
     │ - Use glossary terms consistently. Any term not in the glossary and not │
     │   in an allowed list is flagged.                                        │
     │                                                                         │
     │ Soft targets. These are reported per page in check output as advisory,  │
     │ not gating.                                                             │
     │ - Narrative prose (tutorial, how-to, explanation): mean sentence length │
     │   15–22 words, with variation (sd at least 6).                          │
     │ - Prepositions: 9 or more per 100 words.                                │
     │ - Reference prose: mean of 12–18 words.                                 │
     │                                                                         │
     │ Craft rules, taken from the author's samples:                           │
     │ - Unpack noun stacks with prepositions:                                 │
     │   - "the design retained from training" → "the design built from the    │
     │     training rows".                                                     │
     │   - "Caller precision governs the calculation; this lesson does not     │
     │     enable float64 globally." → "The calculation runs at the precision  │
     │     you configured in JAX. This lesson leaves the default unchanged."   │
     │ - Open a paragraph with framing ("Yet", "However", "Since then", "In    │
     │   practice"), and give each paragraph one idea.                         │
     │ - State what happens first and why it matters. Only then add the limit, │
     │   in its own sentence.                                                  │
     │ - Use a concrete example before an abstraction.                         │
     │                                                                         │
     │ Page-type schemas                                                       │
     │ (infra/schemas/documents/docs-<type>.document-schema.yaml)              │
     │                                                                         │
     │ Schematter 0.2.0 has been verified to support:                          │
     │ - per-section maxTokens;                                                │
     │ - required sections in the schema's own order;                          │
     │ - additionalSections: false;                                            │
     │ - heading pattern/const with minContains/maxContains;                   │
     │ - required blocks: [{type: code}].                                      │
     │                                                                         │
     │ {literalinclude} fences count as code blocks. <!-- statadic:… -->       │
     │ markers are ignored. One Schematter token is roughly 1.5–2 words,       │
     │ because markup inflates the count.                                      │
     │                                                                         │
     │ type: landing                                                           │
     │ Required structure, in order: H1, intro, toctree; no H2                 │

     │                                                                         │
     │ Authoring standard, written into STYLE.md:                              │
     │ 1. Start with a PEP 723 header that pins statadic (git URL with         │
     │    #subdirectory=src/python/packages/statadic until it is on PyPI),     │
     │    marimo and matplotlib. Then uvx marimo edit --sandbox <url> and      │
     │    molab both work.                                                     │
     │ 2. Prose goes in plain mo.md cells: title, intro and step headings. No  │
     │    helper renders prose, and there is no main(), argparse or tempfile   │
     │    scaffolding.                                                         │
     │ 3. Each step is one mo.md heading cell followed by short code cells     │
     │    (about 15 lines or fewer), each ending in a visible output: a        │
     │    report, a table or a figure.                                         │
     │ 4. Visuals use matplotlib figures returned as cell outputs, because     │
     │    they render statically. A small hidden-code style cell sets fonts    │
     │    and colours to match statadic.css.                                   │
     │ 5. mo.ui controls default to the values the prose describes. The static │
     │    page shows the default run, and the prose never depends on a         │
     │    non-default value.                                                   │
     │ 6. Only setup and styling cells use hide_code=True.                     │
     │ 7. The notebook's prose passes the tutorial/how-to schema through       │
     │    marimo export md and the prose checks.                               │

     Philosophy

     1. Diátaxis, one type per page. Each page has a frontmatter type: of
        tutorial, how-to, reference, explanation, landing, evidence or blog. A
        Schematter schema per type fixes the sections, their order and their
        token caps.
     2. The site is for users. Contributor, release and process material goes to
        CONTRIBUTING.md, the package ARCHITECTURE.md, apps/*/README.md and
        infra/release/README.md. History goes to CHANGELOG.md.
     3. One home per fact. A method's assumptions, limits and evidence live
        once, in its reference page under ## Assumptions and limits and ##
        Evidence. Notebooks and how-tos link there once.
     4. Code comes from executed notebooks. Tutorials and how-tos are marimo
        notebooks executed at build. Reference ## Usage snippets are short and
        tested.
     5. The author's voice is the standard. It is quantified and checked.

     Style guide (src/python/apps/docs/STYLE.md)

     Gated by scripts/check_prose.py on every page and on notebook prose
     exported with marimo export md:
     - No semicolons in prose.
     - No sentence over 40 words.
     - No internal vocabulary:
       - IDs matching \bt\d+(\.\d+)*\b, Paper \d or W\d+.
       - Process words: qualification/qualified, campaign, witness, lane,
         ledger, disposition, registration, adjectival retained, brick, door,
         waist, slice, delivery, publication hold.
       - Changelog words: former, no longer, has been removed.
       - evidence pages get a small allow-list.
     - At most one negation sentence per paragraph outside ## Assumptions and
       limits.
     - Glossary terms are used consistently.

     Advisory metrics, printed per page:
     - Narrative mean sentence length of 15–22 words, with sd of 6 or more.
     - 9 or more prepositions per 100 words.
     - Reference mean of 12–18 words.

     Craft:
     - Unpack noun stacks with prepositions. "the retained training design"
       becomes "the design built from the training rows".
     - Write two sentences, not a semicolon.
     - Open paragraphs with framing such as "Yet", "However" or "In practice".
     - Say what happens and why it matters before stating the limit.
     - Use a concrete example before an abstraction.
     - Write interpretation sentences as f-strings over computed values, so the
       prose can't drift from the output.

     Cell rules, from marimo's best-practices and reusing-functions guides:
     - Keep globals few and descriptively named. Use the _ prefix for cell
       locals.
     - Put logic in top-level @app.functions that reference only setup or
       top-level symbols. Steps, Explore and the tests then reuse them through
       from notebook import fn.
     - Don't mutate across cells, and don't use on_change or state handlers.
     - Make cells idempotent, with seeded jax.random.key.
     - Wrap expensive Explore reruns in mo.cache, and gate them with mo.stop
       behind mo.ui.run_button.
     - No print. Show reports with mo.md, mo.plain_text(report.to_text()) or
       mo.callout when the content depends on state.
     - Use hide_code=True only for setup, style and appendix cells.

     Self-contained notebooks. Every notebook carries its own seeded data
     generator in the appendix. molab opens a single file and cannot import
     siblings. Tests assert that the chapter notebooks' generators agree, for
     example across the four OLS lessons.

     Notebook integrity, tests and doctests

     Why this matters. Subagents will write marimo .py files by hand. The main
     failure mode is MB001, unparsable cells: marimo saves a cell it cannot
     parse as app._unparsable_cell(r"""…"""). That notebook still opens in the
     editor but cannot run as a script, and the broken cell never executes.
     MB002–MB005 are the same class of problem: multiple definitions, dependency
     cycles, setup-cell dependencies, and syntax errors.

     Gates, run after every notebook edit (by agents) and in just
     python::docs::check (in CI):
     1. marimo check --strict --select MB,MR,MF <notebooks>.
        - Breaking, runtime and formatting rules are all errors.
        - WASM rules MW001–MW003 stay off; they are irrelevant because JAX never
          runs in Pyodide.
        - Use --format json for agent reports.
     2. A grep gate that fails on _unparsable_cell anywhere under docs/, so it
        holds even if lint config drifts.
     3. python <notebook>.py under JAX_ENABLE_X64=0 and again under =1. This is
        the script-mode run that MB001 breaks.
     4. marimo export md <notebook> followed by Schematter and check_prose.py on
        the prose.
     5. Repairs are explicit. just fmt gains marimo check --fix for auto-fixable
        rules such as MF001 general formatting and MF007 markdown indentation.
        Checks never repair.

     Authoring path for agents.
     - Start from docs/_templates/notebook.py. It contains the PEP 723 header,
       the app.setup cell, every skeleton heading as a pure mo.md cell, and an
       empty Appendix with one example @app.function and one test cell.
     - Keep each cell's code a complete Python statement list.
     - Never leave a mo.md string unterminated, and never write prose outside a
       cell.
     - Run gate 1 after each edit, before moving on.

     In-notebook tests follow marimo's pytest guide.
     - A test cell contains only test_* functions, Test* classes or
       @pytest.fixture functions. A cell mixing in helpers, constants or imports
       is silently skipped.
     - Tests receive values through cell arguments, for example def _(fit,
       make_data): def test_slope_matches_generator(): ….
     - pytest is imported in its own cell, and parametrization uses
       pytest.mark.parametrize.
     - pytest collects statically, so fixtures go in the setup cell or a
       docs/conftest.py. Fixtures in other cells are invisible to it.
     - Test cells sit in ## Appendix with hidden code, and the renderer drops
       the Appendix from the static page.
     - Each notebook header sets [tool.marimo.runtime] reactive_test = false in
       its PEP 723 [tool.marimo] table, so readers in molab don't see test runs.
     - The docs pytest configuration in apps/docs/pyproject.toml collects
       docs/tutorials/*.py and docs/guides/*.py explicitly and keeps
       --strict-markers. Notebook tests are marked e2e.

     Where each kind of test lives.
     - Claims a notebook makes about its own outputs stay in that notebook as
       tests. Example: "the interpretation sentence's slope equals the fitted
       coefficient".
     - Comparisons against independent implementations, such as
       test_reporting_workflow.py's NumPy/HC3 references, stay in
       apps/docs/tests/. They import the notebook's @app.functions. Importing a
       notebook defines the app and its top-level functions without running
       cells.

     Doctests.
     - @app.function helpers with Examples: docstrings run through pytest
       --doctest-modules on the notebook files.
     - For the package: the existing 173 >>> examples (core, discrepancy,
       geometry, inference, sample, association) have no runner anywhere in the
       repo. Wave 5 adds a named doctest lane, --doctest-modules over
       src/statadic. It fixes or removes stale examples, then gates it in just
       check.

     Plotting and widget standard (static first)

     Narrative figures are matplotlib. marimo renders the Figure/Axes given as a
     cell's last expression to SVG when rcParams["savefig.format"] = "svg", and
     otherwise to a 2× PNG (marimo/_output/mpl.py:68-104). Either survives
     static rendering.
     - The setup cell applies statadic_style() with the site's serif fonts, a
       Delft-blue accent, a transparent background, and mid-contrast axes and
       text that stay legible in light and dark.
     - In molab or local dark mode the style also checks mo.app_meta().theme ==
       "dark". Note that it returns light for system.
     - One idea per figure, labelled axes with units, and no chart junk.

     Reactive selection is for Explore only.
     - mo.ui.matplotlib(ax, debounce=True) with ax.value.get_mask(x, y) supports
       box and lasso. Set value={"x": …, "y": …} so the static page shows a
       meaningful initial selection, for example the high-leverage points.
     - mo.ui.altair_chart returns selections as chart.value DataFrames. By
       default it emits Vega-Lite JSON, which needs JavaScript
       (altair_formatters.py:63-111), so it doesn't appear in the narrative
       unless the spike shows it renders statically.
     - mo.mpl.interactive and Plotly are not used.
     - The dataframe chart builder is an authoring aid only. Its generated code
       must be rewritten to the house style.

     wigglystuff widgets (anywidget, used through mo.ui.anywidget(...)) are for
     Explore only. Each is paired with a matplotlib output of its current value,
     so the static page still says something. Intended uses:
     - TangleSlider/TangleChoice for explorable sentences such as "with [80]
       observations and noise [0.4] …";
     - ChartPuck to drag one point and watch leverage and Cook's distance in OLS
       diagnostics;
     - Slider2D for the location and scale shift in energy distance;
     - Matrix to edit covariance or design matrices;
     - PlaySlider to step through permutation or bootstrap draws;
     - EdgeDraw for spatial weight graphs;
     - TangleDistribution in the distributions tutorial.

     Tables. marimo's table and DataFrame outputs are custom elements that may
     not hydrate on a static page. The spike decides between them and the
     fallback of mo.md with a markdown table built from df.head().

  ## A versus B
  - **Option A (`export ipynb --include-outputs` plus myst-nb): rejected.**
    - `nbformat` and `myst_nb` are not in the lock, so it needs two new
  dependencies and a `uv lock` with network access.
    - marimo's `from_ir` also emits the rendered HTML of `mo.md` cells for
  non-pure cells, so table and UI custom elements would still need a custom
  mimetype renderer.
    - A is therefore more machinery with more dependencies, not less.
  - **Option B: chosen, with no new dependencies.**
    - Execution is the public CLI `python -m marimo export session --no-sandbox
  --force-overwrite` on a temp copy of the notebook, in a subprocess, so the
  environment (including `JAX_ENABLE_X64`) is inherited and nothing pollutes
  `docs/`.
    - The parser subclasses `MystParser` and composes one MyST document from the
  notebook:
      - Pure `mo.md` cells (found with marimo's own `get_markdown_from_cell`)
  are emitted verbatim, so their headings reach the TOC, the search index and
  `$..$` math via MyST dollarmath.
      - Shown code becomes a ` ```python ` fence.
      - Outputs go through a custom `marimo-output` directive that renders
  docutils nodes.
    - A non-zero exit from the marimo CLI, or an error output in the session
  JSON, raises `ExtensionError`, so a raising cell fails the build.
    - The first H1 is followed by a `marimo-launch` directive.
    - Appendix: composition stops at the cell whose markdown is `## Appendix`,
  so that heading and everything after it are dropped.

  ## How outputs degrade
  | Output | Rendering |
  |---|---|
  | matplotlib SVG or PNG | `image` node with a data URI, so it is a real
  `<img>` |
  | computed `mo.md` | raw HTML; marimo's `||(..||)` TeX is rewritten to
  `\(..\)` so MathJax renders it |
  | `<pre class='text-xs'>` text and stdout | literal block with language `text`
  |
  | `marimo-table` (pandas, polars, `mo.ui.table`) | real docutils table from
  the embedded row JSON, capped at 20 rows with a "Showing N of M" note; falls
  back to a one-line caption when rows are not inline |
  | `mo.ui.slider` and other `marimo-*` elements | caption such as "Slider Knob:
  3 (interactive in the notebook; shown at its default value)", and downstream
  cells render with default values |
  | `mo.ui.dataframe` | captioned, not rendered as a table |
  | `mo.callout` | raw `<div class="marimo-callout">` |
  | Altair and other Vega-Lite JSON, unknown mimetypes | "Output of type X"
  note; I did not test Altair because it is not installed |

  Computed `mo.md` and callout outputs are raw HTML, so their text is not in the
  search index; pure markdown cells are. Headings must therefore stay in pure
  `mo.md` cells, which the plan already requires.
